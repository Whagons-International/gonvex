# Schema and Migrations

Gonvex application schemas are versioned SQL migrations in the app's
`migrations/` directory. TypeScript module declarations describe function
arguments and results; they do not replace the database schema.

```txt
my-app/
  gonvex/
    tasks.ts
  migrations/
    0001_tasks.sql
```

## Create tables and indexes

```sql
-- migrations/0001_tasks.sql
CREATE TABLE IF NOT EXISTS tasks (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'open',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS tasks_status_idx ON tasks (status);
CREATE INDEX IF NOT EXISTS tasks_updated_at_idx ON tasks (updated_at DESC, id DESC);
```

Migrations are shipped with the TypeScript module artifact and applied by the
runtime in version order. Keep each migration idempotent with `IF NOT EXISTS`
or equivalent guards where appropriate. Use explicit, reviewed SQL for
destructive changes and large backfills.

## Live Query indexes

Index the columns used by Live Query visibility predicates, filters, ordering,
and search. SQLite-specific features (for example FTS5 virtual tables) remain
available to the SQL migration and can be marked server-only in the Live Query plan.

## Generated schema metadata

After `gonvex dev` synchronizes the module and migrations, generated files under
`gonvex/_generated/` expose the observed Control Plane and tenant schema to the
frontend. They are build output and must not be edited manually.

```ts
import { controlPlane, tenant } from "./gonvex/_generated/schema";
```

The runtime rejects schema changes that would silently lose existing data.
Plan destructive changes as explicit migration work with backups and a tested
rollback or restore procedure.
