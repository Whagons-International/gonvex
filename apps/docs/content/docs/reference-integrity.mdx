---
title: Declared reference integrity
description: Enforce application references across SQL writers and soft deletion.
---

Tenant migrations can insert JSON declarations into
`_gonvex_reference_requests`. The Rust migration runner processes them inside
the migration transaction. Gonvex installs the generic ledger tables before
applying application migrations. Applications own table names,
selection paths, lifecycle predicates and deletion policy; the runtime contains
no application-specific relationship list.

The Rust runner installs and enforces this capability. Node schema compilation
retains migration requests for codegen and design diagnostics, without installing
or executing the ledger. A partial Local Replica cannot prove that an uncached
target is missing. Authoritative commit validation remains in Rust; optimistic
local writes may therefore be rejected on replay. This is not local write-time
enforcement, and applications must test their actual codegen and replay path.

A version 1 declaration contains `tables` and `references`. Each table declares
its single primary `key` and a JSONPath `live` predicate. Each reference declares
its unique `name`, `source`, storage `column`, selection `path`, `target`, and
target `state` (`live` or `exists`). For example:

```sql
INSERT INTO _gonvex_reference_requests(declaration) VALUES('{
  "version": 1,
  "tables": [
    {"name":"teams","key":"_id","live":"$.deletedAt == null"},
    {"name":"spaces","key":"_id","live":"$.deletedAt == null"}
  ],
  "references": [
    {"name":"spaces.team","source":"spaces","column":"teamId",
     "path":"$.teamId","target":"teams","state":"live","allowEmpty":true}
  ]
}');
```

Primary key declarations support integer, real, text and binary identities.
Boolean and JSON key encodings are refused, including on empty tables: their
row images can collapse distinct stored values or lose their storage spelling.
Use a separate scalar identity column; Boolean and JSON value columns remain
supported. Schema changes cannot convert an enforced key to these encodings.

New selected IDs must resolve. Deleting the final target, changing its key, or
making it non-live fails if incoming references would remain. A transaction can
explicitly remove or reassign all incoming references and then delete the
target. There is no automatic cascade that could silently change access.
Reducers and bulk row operations use the same `TenantTransaction::commit` path.
The installed staging guard leaves a deferred FK pending until the
shared runtime flush runs; a SQLite writer with foreign keys enabled that omits that flush
cannot commit a relationship-affecting write. Unrelated content edits do not
need a reference flush. Metadata without these guards and the
runtime commit path is not enforcement.

Enforcement uses transactionally maintained target tokens and reference edges
with a deferred foreign key checked at commit. Each tenant database has one
writer at a time, so no concurrent writer can act on a stale snapshot. A failed
transaction leaves the application state unchanged.

Installation never repairs application rows. Version 2 declarations can choose
`"existing":"reject"` to refuse the entire upgrade if any selected target is
missing. The default, `"existing":"inventory"`, records existing violations: they remain visible,
unchanged legacy edges survive unrelated edits, and new edges are enforced.
`SELECT * FROM gonvex_reference_violations` returns violations for an operator
to review. Its results contain application identifiers and need the same access
controls as application data. Repair and eventual constraint validation are
separate operational decisions.

Arrays and nested JSON use JSONPath, with `at` selecting individual containers.
Polymorphic references declare a discriminator and a closed `targets` map.
Alternate keys use `targetKeys`; a nonunique alias requires `multipleOwners`
and a reason. Explicit sentinel, numeric, serialized-JSON and selector-decoder
policies must document the existing consumer behavior they represent.
Storage decoding with `encoding:"json-or-value"` does not split CSV or trim
identifiers. Only an explicit `normalize` policy may do that; commas and
whitespace otherwise remain part of an identity.
Paths support recursive `.**` traversal. The default is lax array access;
the `strict` prefix requires explicit array steps. `valuePrefix` with
`prefixReason` selects tagged values and removes the tag. `ignoreContainingAll`
with `ignoreReason` declares literal markers that together identify non-ID
expressions. These policies are explicit; the runtime does not infer them from
field names or guess expression syntax. Unknown rule policy fields are rejected.

When a value's domain depends on another row, declare a `bindings` projection
and reference `lookup` steps. Each selected configuration version is itself a
referenced token. A parent edit must leave every dependent reference valid;
otherwise reassign or remove the dependents in the same transaction. Lookups
can chain through parents and use the selected container's local keys. A
configuration change queues only its incoming dependents for revalidation
against the transaction's final configuration and row values. Valid edits and
same-transaction reassignments work in either statement order; invalid edits
roll back. Unknown legacy configuration domains still require explicit repair.

Version 2 also supports the following explicit policies. Older runtimes reject
version 2, so deploy a supporting runtime before an application migration uses it.

- A binding's `paths` selects exact object members, such as
  `["$.data.poll.options","$.data.poll.multiple"]`, instead of whole `columns`.
  The projection preserves nesting. Wildcards, arrays and overlapping paths are
  rejected. Updating poll tallies does not version the option domain or enqueue
  other voters. The ledger owns this derived projection and rebuilds it on
  declaration; application code never maintains it. A projection is created by
  an indexed lookup when first referenced. Removing its last reference removes
  the projection, so unused configuration rows do not become duplicate storage.
- An `assert` rule declares a configuration predicate instead of `path`/`target`.
  It requires a lookup, can select containers with `at`, and can compare the
  configuration with `$entry` and `$document`. The configuration token protects
  the parent and revalidates incoming dependents on change. Invalid refinements
  refuse installation, even in inventory mode; they are not grandfathered edges.
- `singleOwner:true` with `ownerReason` requires exactly one physical owner of
  the selected target token. Creating another owner revalidates existing
  incoming references; deleting or moving the last owner still fails the FK.
  Shared aliases without that rule retain their existing multiple-owner policy.

Adding `exclusions` opts into strict storage coverage. Every text, JSON or array
column needs a declared reference, target key, or reasoned boundary such as an
external identity, local key, enum, content, snapshot or derived projection.
Gonvex rechecks coverage in the tenant migration transaction, so an unclassified
schema addition rolls back. Top-level coverage cannot prove the meanings of
arbitrary nested JSON: applications must also review their nested consumers and
keep the declaration and its coverage lint together.

The internal `_gonvex_reference_*` tables are derived implementation state.
Do not expose or write them through application APIs. Applications must not
disable triggers or replace these constraints; privileged DDL is outside the
ordinary-writer guarantee. Installation runs in the single writer transaction and
backfills the ledger, so measure its cost on a disposable representative snapshot before
rolling out a large catalog.

Captured tables share one trigger on the change feed. It queues an event ID
only when declared key, lifecycle or selection inputs change. The pending event
has a native FK to the feed row and a deferred guard FK; row images remain owned
by the feed instead of being copied into a second queue. Statement and savepoint
rollback remove the capture and validation work together. The runtime owns the
compiled input-column projection on the existing reference-table metadata and
rebuilds it from the catalog. Bootstrap receipts include the schema cookie,
catalog digest and dependency-compiler version, so DDL, redeclaration and
compiler upgrades invalidate the installed plan.

A declared table without change capture retains three row-image staging
triggers. Their images contain only declared inputs where dependencies are
known. An unconstrained wildcard retains the full row. A small edit must not
rebuild unrelated reference data.

Compiled policy is grouped by source table and includes its input-column
projection. Equal declarations share one immutable program within the pool
registry; each open database holds its current program alive. Compilation is
single-flight and retryable after failure or cancellation. Weak cache entries
retain no program after its last database closes. Each flush checks that
database's stored declaration digest; a changed or rolled-back declaration
cannot reuse stale policy. Application rows and target, edge and configuration
state remain in the tenant's transaction. Target-only tables do not enter the
outgoing-reference work queue. Installation scans target identities and
then source edges in bounded keyset batches. Only target namespaces used by the
policy are stored; live-state tokens are stored only when a rule needs them.
Inventory cursors retain the original SQLite key storage class rather than its
JSON representation. Source and configuration point lookups use a bounded set
of indexed typed probes, then confirm the exact public identity. Ambiguous
normalized source identities refuse the write instead of selecting a row.
Configuration lookups copy only referenced projections. Commit flushes also process
bounded batches, while the whole application transaction remains atomic.

It is opt-in, not an automatic replacement for every application's native FKs or
JSON references. Prefer native constraints for simple relationships and verify
the cost of large declarations. Keep any remaining application enforcement gaps
explicit; do not treat a clean offline report as write-time protection.
