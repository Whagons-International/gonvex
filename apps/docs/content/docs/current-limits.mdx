# Current Limits

Gonvex is beta software. The active application model is TypeScript Query,
Reducer, and Action modules delivered through a normalized Local Replica,
Replica Collections, and structured Live Queries.

## Implemented today

- TypeScript modules bundled into a self-contained V8 artifact;
- literal language-neutral argument and result schemas with typed codegen;
- versioned SQL migrations and observed scoped schema metadata;
- an authoritative `_gonvex_sync_changes` feed containing committed rows,
  transaction IDs, changed columns, command IDs, and revisions;
- atomic Local Replica transactions with optimistic overlays, IndexedDB, and
  Expo SQLite persistence;
- structured Live Query groups and bounded Replica Collections;
- centralized revisioned visibility with old/new row routing and revocation;
- durable Action outbox and persisted one-shot/recurring scheduling;
- multi-project and tenant-database routing;
- native Google OAuth, Accounts, tenant-local Members, invitations, roles, and
  live session revocation;
- optional S3-compatible file storage and data-file analysis;
- dashboard inspection for projects, tenants, schemas, functions, data, files,
  errors, logs, metrics, realtime connections, and scheduling.

## Current CLI boundary

```bash
npm create gonvex@latest my-app
npx gonvex init
npx gonvex login
npx gonvex project create my-app
npx gonvex auth add google --origin http://localhost:5173
npx gonvex auth doctor
npx gonvex dev

```

Deployment records, immutable release artifacts, fleet rollout controls, and a
generally available hosted service remain roadmap work.

## Realtime and Local Replica limits

Arbitrary SQL remains available to one-shot Queries. Continuous delivery uses
structured Live Queries or bounded Replica Collections.

- portable equality, range, membership, substring, boolean, sort, and window
  operators can run against cached rows;
- SQLite-specific expressions are online-only;
- Replica Collections are bounded structured entity sets, not an implicit copy
  of an entire tenant database;
- Live Query windows remain server-authoritative for large datasets;
- offline results report `complete` or `partial` and never pretend a partial
  cache is the complete server result;
- every delivered table needs one centralized visibility plan;
- interactive Reducers require an optimistic transaction or an explicit
  reviewed non-optimistic reason;
- complex nested windows may use a full replacement when a keyed delta is not
  safe.

## Identity and tenancy limits

The Control Plane directory is a routing projection, not the final security
authority. Tenant access is checked against the active tenant database's
Member record. Cross-tenant profile fields may be projected into Members, but
business data remains tenant-local.

Backup/restore orchestration, staged schema rollouts, tenant moves, custom role
editing, quotas, billing, additional identity providers, enterprise SSO, SCIM,
recovery flows, and hosted-control-plane hardening remain incomplete.

## Production guidance

Plan explicitly for migration previews and backfills, deployment/versioning and
rollback, tenant fleet backups, scheduler retention/dead letters, identity and
audit requirements, and operating the self-hosted runtime. No public managed
Gonvex service is generally available yet.

## SQLite storage

Every database is a SQLite file in the runtime's data directory
(`GONVEX_DATA_DIR`): `control.db` for the Control Plane and one file per tenant
or single-database project. There is no database server, connection pool budget
or network round trip on the query path. The trade-offs are:

- **One runtime per data directory.** The runtime takes an exclusive lock file
  (`.gonvex.lock`) at start and refuses to start while another process holds
  it. Deploys must stop the old process before the new one opens the files;
  rolling deploys that run two runtimes on one volume are not supported, so a
  runtime upgrade has a short restart gap.
- **One writer per database file.** Reducers and other writes for one tenant run
  one at a time on that file's writer connection. Reads run concurrently on a
  small read-only pool, each on one consistent WAL snapshot. Different tenants
  write in parallel.
- **Vertical scaling only.** A project's tenants live on the runtime host's
  volume. Horizontal runtime replicas over shared tenant files are not
  supported.
- **Backups are file snapshots.** The production profile copies every database
  daily with SQLite's online backup API. Continuous replication (Litestream) is
  a planned follow-up.

`GONVEX_SQLITE_SYNCHRONOUS` selects `full` (default) or `normal`; `normal` can
lose the last commits on power loss, never on a process crash. Measurements and
the full storage contract are in
[SQLite storage](https://github.com/Whagons-International/gonvex/blob/main/docs/sqlite-storage.md).
