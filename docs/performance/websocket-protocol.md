# Gonvex WebSocket protocol audit

Audited `staging` at `d860fb7e` on 2026-10-23. The production changes are deliberately small: enable TCP_NODELAY on accepted runtime sockets, and negotiate omission of transaction `oldValue`. JSON, DEFLATE settings, complete new projections, resume, integrity, authorization and storage ordering retain their existing contracts. Experiments live in [an isolated benchmark package](../../scripts/bench-websocket/README.md), with no new production dependencies.

The largest measured latency opportunity was outside serialization. The existing listener did not set TCP_NODELAY. In a 100-trial browser/LocalReplica loopback comparison, enabling it changed small-update p50/p95/p99 from 41.74/42.78/42.95 ms to 0.66/0.97/3.98 ms. The same four frames and 1,797 WebSocket bytes crossed the TCP counter in both runs. Both proxy sockets used TCP_NODELAY, isolating the accepted Rust socket. See [the listener](../../rust/crates/runtime/src/main.rs), [the baseline receipt](websocket-2026-10-23/nagle.json) and [the TCP_NODELAY receipt](websocket-2026-10-23/nodelay.json). This is a controlled transport-to-replica result, not a production WAN latency estimate.

The audit corrected several assumptions:

| Path | What staging actually does | Consequence |
| --- | --- | --- |
| Change feed | Reads complete old/new JSONB values from `_gonvex_sync_changes`. [change_feed.rs](../../rust/crates/runtime/src/change_feed.rs) | Old images remain necessary inside the server for visibility transitions, resume reconstruction and membership decisions. Do not remove them from the feed. |
| Replica transaction | Projects visible values, normalizes the union of overlapping collection projections, then sends `oldValue`, `newValue`, operation and changed columns. [apply_feed_event and normalize_entity_changes](../../rust/crates/runtime/src/replica.rs) | The browser does not consume old images. A normalized new value is a complete projection union, not necessarily a complete database row. |
| Collection delta | Sends complete projected upserts and deleted IDs after the entity transaction. Then sends ready/integrity metadata and an ordered connection watermark. [replica.rs](../../rust/crates/runtime/src/replica.rs), [feed dispatch](../../rust/crates/runtime/src/lib.rs) | New row values cross the wire twice. The consumers have different entity versus membership/hash responsibilities, so deleting one message outright is unsafe. |
| Irrelevant changes | Already suppresses unrelated collection ready fan-out; unchanged snapshot diffs emit no row upserts. The incremental source path still constructs upserts for visible rows even when only an unprojected column changed. | Further projection-no-op suppression is possible, but must preserve multiple changes to one row, visibility transitions and commit acknowledgements. It is not part of this patch. |
| Structured live queries | Re-executes affected SQL plans, compares results, and sends a complete `query.result` when changed. Resume can return `query.progress`. [live_query.rs](../../rust/crates/runtime/src/live_query.rs) | TypeScript keyed-patch capabilities and protocol types do not mean this Rust path emits field patches. SQL/result hashing can dominate independently of WebSocket encoding. |
| Reconnect | Checks collection epoch, retained revision and hashes/digest. Repairs with changed complete rows or a complete snapshot. `replica.needHashes` repairs aggregate mismatches. [open_replica_negotiated](../../rust/crates/runtime/src/replica.rs) | Keep the full-row fallback. Removing old wire images does not change any replay or repair decision. |

The browser applies a transaction to its own local row and persists new projections through per-field authority. Neither built-in IndexedDB adapter uses `oldValue`. See [SDK dispatch](../../packages/client/src/index.ts), [LocalReplica](../../packages/client/src/local-replica.ts), [record authority](../../packages/client/src/replica-record.ts), [engine storage](../../packages/client/src/indexeddb-engine.ts) and [legacy storage](../../packages/client/src/indexeddb-replica.ts).

`replicaNoOldValues: 1` is an optional auth capability, advertised by both protocol peers. The Rust connection may omit old images only after a successful auth carrying exactly version 1. Absent and unknown versions retain the legacy transaction. New SDKs still read legacy transactions from old servers. Inserts, deletes, full new projections, provenance, origin command IDs, revisions, digest certificates and watermarks retain their existing representation. Native canonical transactions already omitted old images before this change. Wire preparation runs after projection/visibility normalization, so it cannot affect permission decisions. The [protocol encoder](../../rust/crates/protocol/src/replica_wire.rs) reuses its serialized JSON for sending. It retains the legacy frame when omission would move a previously compression-eligible transaction below the actual negotiated threshold. Plain fallback has no such guard. Small compact frames count old-image bytes without allocating a second row buffer; large compact frames skip that pass.

With the current level-1, 12-bit, 1,024-byte DEFLATE configuration, the encoded comparison is:

| Workload | Existing JSON bytes | JSON without old images | Experimental field patches | Saving from old-image omission |
| --- | ---: | ---: | ---: | ---: |
| Small single-field update | 1,797 | 1,402 | 758 | 22.0% |
| 16 KiB row, one field changed | 27,059 | 18,292 | 758 | 32.4% |
| 100 changed rows | 27,912 | 25,903 | 1,472 | 7.2% |
| 1,000 changed rows | 269,109 | 248,778 | 9,077 | 7.6% |

A separate threshold sweep caught regressions that the original small/large cases missed. With a 512-character description, the production-serializer boundary fixture grew from 1,873 to 2,106 bytes under naive omission by disabling compression. The production threshold guard retains the legacy encoding in that case. The boundary experiment invokes the production protocol encoder, including Unicode, escapes and exact threshold equality tests. The main codec table measures serialized payloads; feed construction and wire preparation are separate costs. In a separate typed-protocol measurement, encoding plus the production guard took 0.92 microseconds for the small transaction versus 0.79 for legacy encoding, and 4.88 versus 9.45 microseconds for the large-row transaction. The 100-row case was 70 versus 66 microseconds, and the 1,000-row case 2.08 versus 2.26 ms. These samples include moving and dropping the old images in the guard but exclude fixture cloning. The guard is not a universal CPU-speed claim.

The main matrix uses protocol-shaped `serde_json::Value` fixtures. The boundary experiment uses the actual typed `ServerMessage` serializer; its envelope field order changes some compressed totals by a few bytes.

These totals include all server WebSocket frame headers for a transaction, delta, ready and watermark. The TCP proxy verifies actual compressed frame bytes against the Rust matrix. They exclude TCP/IP, TLS, benchmark control messages and handshakes. Small messages remain below the production compression threshold individually, even when the sum of a transaction's frames exceeds it.

In the release Rust microbenchmark, omitting old images changed 1,000-row JSON encoding p50 from 988 to 643 microseconds. Peak additional live encoder allocation dropped from 1,701,888 to 850,944 bytes. This measures serialization buffers, not the runtime's entire row/feed heap. The unchanged feed still allocates old projections before wire preparation. Instrumented allocation counts and timings are available for every codec/compression combination.

Field patches provide the largest bandwidth saving on these workloads. The experiment uses top-level `set` and explicit `unset`, with null as a normal value and independent base/new revisions. Its seeded transition model covers deletion, null, duplicates, delayed messages, missing bases and full-row recovery. It reconstructs complete projections before calling the real LocalReplica/storage interfaces. Patch construction, persisted base versions, permission changes and production repair dispatch are not included in the timed candidate. Its favorable results therefore do not prove a production patch protocol is ready.

A production patch contract should bind each base to tenant scope, visibility/projection generation, epoch and record version. A duplicate must be idempotent, a stale message must not overwrite newer fields, and a missing/mismatched base must leave both rows and the cursor uncommitted while requesting an authoritative complete row or snapshot. Persist row authority, explicit field tombstones and cursor in the same transaction. Keep full images for inserts, projection changes, cache eviction, lost bases and resynchronization. Overlapping projections and multiple tabs require the existing per-field authority, not a single global last-seen transaction revision. Full repair and patch application must reproduce the exact collection digest before ready status. Compare complete compressed batches when selecting patches; compressing two candidate encodings for every small row would add avoidable hot-path CPU work.

The compression audit confirms RFC 7692 negotiation in [negotiation.rs](../../rust/crates/websocket/src/negotiation.rs) and bounded inflation in [inflate.rs](../../rust/crates/websocket/src/inflate.rs). [Config](../../rust/crates/runtime/src/config.rs) enables permessage-deflate by default and exposes `GONVEX_WS_COMPRESSION_THRESHOLD`, default 1,024. The [encoder](../../rust/crates/websocket/src/lib.rs) fixes level 1, negotiates a server window of at most 12 bits, creates codec state per message and sends compressed data only if smaller. Both directions disable context takeover. This avoids retained codec state on idle connections; per-message compression still allocates codec state and output buffers.

For the 10k-row complete snapshot, level 1 produced 1,207,205 framed bytes at 7.79 ms compression p50. Level 3 produced 867,017 bytes at 16.30 ms; level 6 produced 808,894 bytes at 17.79 ms. Zstd level 3 produced 764,647 bytes at 8.09 ms. Brotli quality 4 produced 760,741 bytes at 76.43 ms. The 4 KiB Zstd dictionary was trained on separate generated records. It helped small messages but worsened some large batches/snapshots, and its distribution cost is excluded. Dictionary support was not tested in the browser. These are trade-offs, not grounds for globally increasing compression work.

A threshold of 256 compressed the small baseline to 1,185 bytes instead of 1,797, at 11.3 microseconds of server compression instead of 0.3. A 4,096-byte threshold did not improve the large cases. Keep the production defaults for now. Tune the existing threshold setting against an application's message-size distribution and CPU/bandwidth budget. Zstd and Brotli require application framing, decoder delivery, decompressed-size limits, failure handling and protection against double compression in browsers. GZIP offers no new compression algorithm and was not introduced.

MessagePack uses Rust `rmp-serde` named maps and browser `@msgpack/msgpack`. It preserves dynamic field names but does not remove them. On the 1,000-row baseline, compressed MessagePack is 256,268 bytes versus JSON's 269,109, a 4.8% saving. On the complete snapshot it saves 4.1%. Browser eager decoding of the 1,000-row baseline took 7.42 ms p50 for MessagePack versus 3.11 ms for JSON, including UTF-8 conversion for JSON. Snapshot decoding was 24.77 versus 9.68 ms. Some transport-to-memory cases still favor MessagePack, so native JSON decoding speed alone is not the final decision. Keep JSON as the supported default until the durable pipeline and memory results justify another negotiated codec.

MessagePack can represent signed/unsigned 64-bit integers and binary data. Its JavaScript library requires explicit BigInt handling for exact int64/uint64 values. The benchmark tests both boundaries, null and binary bytes. Gonvex's current browser `JsonValue` and JSON-string storage do not accept arbitrary BigInt or Uint8Array values. Changing the envelope codec alone does not fix that contract. Native canonical rows currently preserve exact source integers without parsing them through JavaScript numbers. A future codec must specify typed-value tags, safe revision bounds, hashing/canonicalization and storage conversions, and keep the initial handshake readable by legacy peers. Select the codec only after mutual versioned capability acknowledgement. See [MessagePack's options](https://github.com/msgpack/msgpack-javascript/blob/main/README.md) and [named-map encoding](https://docs.rs/rmp-serde/1.3.1/rmp_serde/encode/fn.to_vec_named.html).

The dynamic Protocol Buffers comparison uses the actual protobuf Value/Struct representation, including conversion to/from ordinary objects. Its 1,000-row baseline was 1,412,798 raw bytes versus JSON's 1,271,002, with 20.34 ms browser decode p50 versus 3.11 ms. This does not evaluate generated per-table protobuf schemas. The standard dynamic numeric value is a double, so it also needs a separate exact-int64 contract. See [the well-known types](https://protobuf.dev/reference/protobuf/google.protobuf/).

The FlatBuffers alternative was evaluated through its schema-less FlexBuffers JavaScript implementation, version 25.9.23. Eager decoding failed on the unmodified timestamp-bearing workloads with `TypeError: Cannot mix BigInt and other types, use explicit conversions`. The runner records the failures. Lazy envelope access works, but reading only `type` is not comparable to decoding and storing all rows. No typed FlatBuffers throughput claim is made. Typed schemas and lazy access remain plausible for native snapshot storage, but materializing JavaScript objects discards much of that advantage. See [FlexBuffers](https://flatbuffers.dev/flexbuffers/) and [JavaScript FlatBuffers](https://flatbuffers.dev/languages/javascript/).

Initial snapshots already have a separate delivery path. Legacy browser pages are limited to 512 rows and about 256 KiB, with one page pumped per socket turn. The browser [SnapshotPageStager](../../packages/client/src/snapshot-pages.ts) validates ordering, keys, metadata, budgets and a final digest before activation. It retains all decoded rows and hashes until completion, so frame bounds do not make total JavaScript memory independent of collection size. The server also retains its materialized subscription rows. Large collections need explicit row/byte budgets.

The native path in [snapshot_delivery.rs](../../rust/crates/runtime/src/snapshot_delivery.rs) requires `replicaNativeRows`, `replicaSetDigest` and `replicaSnapshotPages`, all version 1. It sends canonical JSON row strings inside binary WebSocket frames. It is not a FlatBuffers or MessagePack row layout. The existing limits are eight in-flight frames and 512 KiB per connection, a 128 KiB frame ceiling, and 256 snapshot subscriptions. Credits return only after cumulative durable staging ACKs; duplicates do not create credit, and canceled generations retain credit for bytes already in flight. A ready certificate waits for the final durable acknowledgement.

The browser SDK currently advertises only the legacy page capability and parses message data as JSON text. It does not negotiate native canonical snapshots or send their durable ACKs. Enabling those capability bits alone would be incorrect. The canonical snapshot experiment measures JS parsing of row strings, not direct binary storage. A browser implementation should stage each generation in IndexedDB or OPFS, persist pages before acknowledging them, verify the existing digest contract and atomically activate the completed generation. Keep live updates fenced behind that baseline and bound canceled/incomplete generations. This is the next credible memory project, rather than replacing ordinary application objects with a new binary object model.

The incremental order recommended by the measurements is:

1. Ship TCP_NODELAY and negotiated old-image omission. Their behavior is small, tested and backward compatible.
2. Profile durable row/membership writes and snapshot staging. Preserve ownership boundaries and avoid re-cloning rows already owned by storage. Buffer reuse must not expose mutation through frozen/shared rows or transfer an ArrayBuffer still in use.
3. Implement negotiated field patches only with durable base/authority tracking and complete-row repair. Separately consider transaction-to-delta row references to remove the second new-row copy while retaining collection-specific hashes and membership.
4. Pilot Zstd for large snapshots and MessagePack for workloads where the complete pipeline wins. Keep JSON/permessage-deflate fallback. Do not generalize the codec-only results to every browser or record distribution.
5. Explore native canonical staging before typed FlatBuffers. Formalize epoch, scope, row authority, tombstones, ACK credit and activation transitions before changing them. A small state-machine model plus generated fault sequences can test dropped/duplicated pages, stale cursors, crashes between data and checkpoint, canceled snapshots, eviction, projection changes and peer-tab races. The experimental patch model is not formal verification of Gonvex's protocol.

The benchmark uses synthetic task records, nested values, nullable fields, short prose with varied tokens, large descriptions, batches and initial snapshots. It does not use customer data. The expired-cursor fixture benchmarks full-resnapshot encoding only. A real auth/reconnect handshake, SQL/feed processing, SDK dispatch, digest hashing, optimistic command replay, TLS and WAN effects are excluded from the transport-to-storage timing. Baseline setup and cleanup are outside timed trials. Snapshot tails have only eight samples and should not be treated as reliable p95/p99. The byte-counting TCP proxy adds measurement overhead. Native builds ran concurrently with part of the first memory run, so latency differences are exploratory. The final IndexedDB trials run after those builds, with an explicit empty database check before every seed and deletion of the actual engine database after every trial. TCP/IP/TLS header and packet counts were not measured; TCP_NODELAY can trade TCP batching for lower latency. Host load and versions are recorded; this was a shared workstation, not an isolated capacity test. GC/task totals include untimed setup, and sampled peak heap is a lower bound. The results support incremental choices, not production latency guarantees.
