# 0030: K07 Reducer path: findings and proposals

Date: 2026-11-11. Status: **proposed** (K07). Affects: K01, K05, K08, K10, K11, P03, V01.

K07 implements `reducer.call`, `reducer.callMany` and `__gonvex.reducerReceipt` in the tenant object
(`cloudflare/kernel/reducer/`), and the two 0028 follow-ups (mixed-mode FK check, capture on K01's real session).
These are the places where the kernel cannot or does not copy Rust byte for byte, and what the next packages need.

| # | Finding | Proposal |
|---|---|---|
| 1 | 0009 rule 1 describes a tombstone with `expired = 1`. Rust's `_gonvex_reducer_idempotency` has no such column. A committed Rust receipt never has a NULL result: the claim and the result commit in the same transaction, and a failed Reducer rolls both back. | **Encode the tombstone as `result IS NULL`** on a committed row. The table stays byte-identical to Rust's (`sqlite_schema` text included), so P03 round trips and M02 need nothing new. Rust's own receipt query already reads such a row as "not complete". The kernel answers it with 0009 rule 3 (`Reducer receipt expired`, rejected). Rules 2 to 5 are unchanged: tombstones are deleted 365 days after their result expired, in pages of 500 on the tenant alarm, never inside a Reducer. |
| 2 | Rust claims the receipt at the Reducer's first database call. A module that throws before touching the database therefore reports its own error, even when its key is already committed. That is only possible when the same key comes back with different arguments. | The kernel serializes the Reducer path per object, so it reads the receipt before the module runs and replays. **Accept** this as the one difference. Every scenario in `receipt-*` is unaffected (`receipt-lost-reply` step 5 sends other arguments to a module that reads the database first). |
| 3 | 0028 §3 says K04 and K07 must refuse application writes while `gateClosed()`, "answering with Rust's transient error class". It names no text. | `module database capability failed: tenant schema migration in progress; retry`, class `transient` (retryable, so the SDK keeps the intent). Rust never sends it: its writers wait on the schema lock. |
| 4 | The watermark that completes a call depends on the socket's subscriptions (`min(cursors).max(sent)`, lib.rs 3296-3310). Those live with replica delivery (K10). | The Reducer path takes `subscriptionFloor(socket)` from K10. Until K10 lands, every socket counts as having no subscription. That is Rust's behavior for a socket that subscribed to nothing, and no kernel socket can subscribe yet. **K10 must provide the floor** and make the batch urgent when the call does not complete at once. |
| 5 | A call that changes the caller's own Member (lib.rs `own_membership_changed`) must make the session drop its tenant scope, then send the watermark. The tenant object only returns frames to the gateway. | The object delivers `membershipChanged` to the tenant's gateways (K05 `TenantGateways.deliver`) after the reply. The session queues delivery behind the frame it is answering, so the client sees Rust's order: `reducer.result`, `auth.error membership-changed`, `replica.watermark`. When K10 delivers commits, it sends the same notice for other Members' sockets. A repeated notice is a no-op. |
| 6 | **K01 bug found by integration.** K01's foreign-key model ran `pragma_foreign_key_list` over every table. Once an object uses `storage.kv` (K02's migrator, K05's gateway registry and K07 all do), the platform's `_cf_KV` table refuses that read with `SQLITE_AUTH` ("not authorized"), and every Reducer's FK check failed. | Fixed in `kernel/storage/foreign-keys.ts`: `_cf_*` tables are skipped (they have no foreign keys). A K01 test covers it. |
| 7 | 0028 §2d: mixed mode. | `writeTracking: "mixed"` in K01 plus a `rowReported(table)` predicate. The predicate is true for captured entity tables with rowids, the tables K03's `finalize` reports rows for. Those stay row-level. Every other written table is checked per table: derived, metadata, record storage and `_gonvex_*`. The tenant object reads the predicate once per schema generation. K03's `capture-parity` test now runs on K01's real `StorageSession` in mixed mode (0028 §2e), and all 114 change rows still match. |
| 8 | `reducer-errors` step "transient: invocation deadline" (`errors.spin`, a pure `for(;;){}`) never returns on **local** workerd, which enforces no CPU limit. The tenant object stays busy, and every later call to that tenant hangs. | This is already ruled platform-forced (0021 §5e, 0022 §5c). It only means the kernel run of `reducer-errors` must happen on the platform (`limits.cpu_ms = 5000`) or skip that step locally. **V01 decides.** K07 did not run `reducer-errors` against the kernel. |
| 9 | Receipt results larger than 2 MB cannot be stored in one row on the platform (CONTRACT E.a.4). Local workerd does not enforce the limit (a 3 MB receipt stores), so the platform outcome is not measured yet. | On the platform the receipt insert should fail inside the Reducer's transaction, so the call fails with `module database capability failed: …` and nothing commits; Rust would store it. **Follow-up (credentials outage):** confirm on the platform, and count the Whagons Reducers whose results exceed 2 MB from the Reducer log feed (P04). |
| 10 | Declared reference integrity (`reference_integrity.rs`, 0028 §3 item 6). | Ported whole into `kernel/reducer/reference/`: ledger, `flush`, `declare`, coverage and JSON path, with Rust's unit and integration tests. The flush runs before K03's finalize in every Reducer. K02's `after_migration` hook now runs the real engine instead of refusing declared catalogs. One platform limit is new: a declared table wider than about 240 columns would make a staging trigger over 100 KB. |
| 11 | **Rows read on first writes.** In the real Whagons bundle bench (`kernel/reducer/bench/`, S2's 2,396-object subset), 87 % of the rows the committed Reducers read are K03's per-table probe in `finalize` `reportRows`. It runs once per table per object and schema generation, and does two by-name lookups in `sqlite_schema`, which has no index: about 4,840 rows each time, and about 16,600 on the full Whagons schema. The receipt-table check (`ensure_reducer_idempotency`, three `sqlite_schema` probes) reads about 7,200 rows once per generation. | Not a correctness issue. **R04** (catalog and wake costs) should feed `reportRows` from the one `sqlite_schema` scan the tenant object already makes per generation for `rowReported`, and fold the receipt probe into it. Without finalize and the FK model, the committed Whagons calls read 1,531 rows (K04's host alone: 1,227). |

## What the next packages get

- **K10:** `ReducerPathOptions.subscriptionFloor` (finding 4); `CommittedCall` through `onCommit` for delivery; K03's
  `ChangeWake` notices as before.
- **K11:** `onCommit` reports `outboxWritten` (Rust's `outbox_written`). The drain and the alarm multiplexing are K11's.
  The receipt expiry is one more alarm duty (`KernelTenant.pruneReceipts`, at most hourly).
- **K08:** queries go through the same per-object `serial` queue as Reducers, because K01 runs one invocation at a time.
  The receipt query is already routed (`query.call` of `__gonvex.reducerReceipt`).
- **K19:** the tenant object's `activate(projectId, manifest, planId)` is the per-tenant `/dev/sync` step: migrate to
  the release plan, then activate the generation whose artifact hash the manifest names. The bundle must be in the
  Worker version.
