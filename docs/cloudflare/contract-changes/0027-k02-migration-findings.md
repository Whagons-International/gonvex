# 0027: Migrations and provisioning in the kernel (K02 findings)

Date: 2026-11-11. Status: **proposed** (K02). Affects: K19, K07, K01, R03.

Measured in local workerd with the Whagons staging migrations (`whagons5-client` `a6de676951`) and compared with a
tenant that Rust's `gonvex-store` `provision_tenant_database` provisioned from the same files
(`cloudflare/kernel/migrate/verify/`).

| # | Finding | Proposal |
|---|---|---|
| 1 | The A01 transform over the whole history takes about 9–10 s of CPU, and its heap peaks above 128 MB in Node (it fails at `--max-old-space-size=128`, succeeds at 192). The transform needs the whole history before it can plan a new migration. A tenant object (128 MB, `cpu_ms` 5000 per 0022 §3b) cannot run it, and neither can a plain Worker isolate. | **Plans are built once per release, outside the object** (G0-10's "built once per release"). An object reads a manifest plus one chunk per transaction from a `PlanStore`. K19 decides where the build runs (a Container, the CI build, or a reduced-memory transform from A01) and where plans are stored (next to the bundle in R2: `R2PlanStore`). |
| 2 | Rust ends a `-- gonvex:foreign-key-rebuild` migration with `pragma_foreign_key_check LIMIT 1` over the whole database. On the Whagons schema in workerd that runs out of SQLite memory (S1 saw the same), which breaks the object's output gate and resets it. On a large tenant it would also overrun the event's CPU. | The kernel checks **one table at a time** (`pragma_foreign_key_check(<table>)`, in `sqlite_schema` order) over several events, with foreign keys off and the gate closed. Then it writes the ledger row and finalizes. The error text is Rust's. If several tables violate, the reported one can differ from Rust's choice. |
| 3 | A migration runs as several storage transactions (T7). Atomicity across them comes from a **point-in-time bookmark** taken before each transactional migration. A failure after a committed chunk restores it (`onNextSessionRestoreBookmark`, then the next event aborts). That matches Rust: the failing migration rolls back and earlier ones stay. Local workerd has no point-in-time recovery, so there the object reports that the committed chunks remain. | Accept. Application writes must wait while `gateClosed()` (Rust's schema lock). K04/K07 check it. |
| 4 | Between the chunks of one migration on a tenant that already has record capture, staged `_gonvex_record_pending` rows would fail the commit through their deferred guard foreign key, and a deferred-FK failure resets the object. | The rows wait in `_gonvex_st_migrate_record_stash`, which exists only mid-migration, and go back before the next chunk. The migration still finalizes once, with the first images. |
| 5 | `-- gonvex:no-transaction`: a Durable Object has no autocommit outside its implicit transaction. | Statements run outside `transactionSync`, so earlier statements stay after a failure (Rust's documented semantics). The ledger row is written last. `VACUUM` is refused with a clear error (E.a.6). |
| 6 | `reference_integrity::after_migration` has a full declared-reference engine (`_gonvex_reference_requests`). Whagons declares no catalog. | The kernel runs it as a no-op when nothing is declared, and **fails loudly** if a catalog is declared, until K07 provides the engine. |
| 7 | Rust re-runs `install_tenant_identity` on every provision. A Whagons migration rebuilds `members`, which drops its three membership-outbox triggers, so a Rust tenant has them only after its **second** provision. | The kernel does the same: every release re-runs the prelude. A rolled-out object equals a Rust tenant provisioned twice. |
| 8 | `PRAGMA foreign_keys` is a no-op inside a transaction, and any storage write in an event opens the implicit one. | The kernel switches it right after `storage.sync()`, checks that it took effect, and switches it again on each new session while a rebuild is in progress. |
